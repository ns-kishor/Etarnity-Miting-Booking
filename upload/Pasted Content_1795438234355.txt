**Date:** November 2026  
**Product Type:** Full-Stack Web Application

# 1. PROJECT OVERVIEW

## 1.1 Product Vision

Develop a modern, premium, minimal and fully responsive online meeting booking platform for **Etarnity Global Innovation**.

The platform will allow external visitors, potential clients, business partners, investors and other interested individuals to discover the company's board members, explore their professional expertise, check their availability and book meetings directly with their preferred board member.

Additionally, each board member will have an individual dashboard to manage meeting requests, availability schedules and personal profiles.

A Super Admin will have complete administrative control over the entire platform.

## 1.2 Primary Objectives

- Make meeting booking simple and accessible.
- Showcase the company's board members professionally.
- Eliminate double bookings and scheduling conflicts.
- Give board members independent meeting management capabilities.
- Provide centralized control through a Super Admin panel.
- Deliver a premium user experience across all devices.

## 1.3 User Roles

The application will have three primary user roles:

| Role | Responsibilities |
|---|---|
| Visitor / Client | Discover board members and book meetings |
| Board Member | Manage bookings, schedules and profile |
| Super Admin | Manage the entire platform |

# 3. MEETING BOOKING SYSTEM

This is the most important feature of the entire application.

Each board member must have an individual booking page.

**Suggested URL structure:**

`/book/[board-member-slug]`

Example:

`/book/kishor-biswas`

## 3.1 Booking Page Layout

The booking page should use a clean three-part layout on desktop.

| Section | Content |
|---|---|
| Left | Meeting information and meeting methods |
| Center | Availability calendar |
| Right | Available time slots |

On smaller screens, these sections should stack vertically in a logical order.

### Left Section — Meeting Information

Display:

- Board member's name and profile photo.
- Designation.
- Meeting duration.
- Short meeting description.
- Available meeting methods.
- Meeting instructions.

Meeting duration must be configurable by the board member.

For example:

- 15 Minutes
- 30 Minutes
- 45 Minutes
- 60 Minutes

The board member can enable or disable specific durations.

## 3.2 Availability Calendar

Create an interactive calendar.

### Calendar Requirements

- Display current month and year.
- Previous and next month navigation.
- Highlight available dates.
- Disable unavailable dates.
- Disable past dates.
- Clearly distinguish the selected date.
- Display availability using subtle indicators.
- Prevent selection of dates outside the booking window.

When a visitor selects a date, the available time slots for that date must appear dynamically.

## 3.3 Available Time Slots

Display time slots on the right side of the calendar.

Example:

**Monday, December 07**

Available time slots:

- 10:00 AM — Available
- 11:00 AM — Time Already Booked
- 02:00 PM — Available
- 03:00 PM — Available

### Slot Statuses

Every slot must have a clear status:

- Available — Selectable.
- Pending — Temporarily unavailable while a booking request is being processed.
- Booked — Not selectable.
- Unavailable — Not selectable due to board member's schedule.

Booked slots must display:

`Time Already Booked`

Do not allow visitors to select occupied time slots.

### Critical Booking Logic

Implement server-side booking validation.

The system must:

1. Fetch availability from the database.
2. Check existing bookings.
3. Temporarily reserve a selected slot during the booking process.
4. Prevent simultaneous booking attempts from claiming the same slot.
5. Revalidate availability when the visitor submits the form.
6. Release expired temporary reservations automatically.

Use database transactions or equivalent atomic locking to guarantee that two visitors cannot successfully reserve the same board member's time slot.

**Important:** A pending booking request must also block the corresponding slot until it is approved, rejected or expires, according to the configured booking policy.

## 3.4 Meeting Method Selection

Display available meeting methods in the left section.

Possible options:

- Google Meet
- Zoom
- Microsoft Teams
- Phone Call
- Physical / In-person Meeting

These options must be configurable by individual board members.

A visitor can select only the methods enabled by the relevant board member.

If a meeting method requires additional information, display the appropriate conditional fields.

For example, an in-person meeting may require a preferred location.

## 3.5 Booking Steps

Implement a three-step booking flow.

**Step 01 — Select Date & Time**

**Step 02 — Complete Your Details**

**Step 03 — Confirmation**

The Next button should remain disabled until all required selections are completed.

## 6.3 Schedule Management

This is where each board member manages their personal meeting availability.

### Availability Settings

The board member must be able to:

1. Set working days.
2. Set daily available hours.
3. Add multiple availability periods per day.
4. Set meeting durations.
5. Set breaks.
6. Block specific dates.
7. Add holidays.
8. Set minimum advance booking time.
9. Set maximum future booking window.
10. Configure booking buffer time.
11. Set timezone.
12. Enable or disable specific meeting methods.

### Example Schedule

| Day | Availability |
|---|---|
| Monday | 10 AM – 5 PM |
| Tuesday | 10 AM – 5 PM |
| Wednesday | 2 PM – 6 PM |
| Thursday | 10 AM – 5 PM |
| Friday | 10 AM – 1 PM |
| Saturday | Unavailable |
| Sunday | Unavailable |

All schedules must be editable.

### Custom Date Availability

Board members should also be able to:

- Add availability on normally unavailable days.
- Block a particular date.
- Modify working hours for a specific date.
- Create one-time exceptions.

### Important Scheduling Logic

Availability must be calculated using:

`Weekly Schedule + Date Exceptions - Existing Bookings - Buffer Time`

The system must never display unavailable or occupied slots as bookable.

If a board member changes their schedule after meetings have already been approved, existing bookings must remain intact. The system should warn the board member before any conflicting changes.

# 9. TECHNICAL ARCHITECTURE

The platform must be a real, database-driven application, not a static website or frontend-only prototype.

### Recommended Technology Stack

| Layer | Recommended Technology |
|---|---|
| Frontend | Next.js |
| Language | TypeScript |
| Styling | Tailwind CSS |
| UI Components | Custom reusable components |
| Animation | Framer Motion |
| Database | Supabase PostgreSQL |
| Authentication | Supabase Auth |
| Backend | Next.js Server Actions / API Routes |
| Image Storage | Supabase Storage |
| Email | Resend |
| Spam Protection | Cloudflare Turnstile |
| Deployment | Vercel |
| Version Control | GitHub |

The implementation may use equivalent technologies if there is a strong technical reason, but all functional requirements must be preserved.

## 9.1 Database Structure

Recommended primary database tables:

| Table | Purpose |
|---|---|
| users | Authentication and account roles |
| board_members | Professional profiles |
| bookings | Meeting booking records |
| availability_rules | Weekly schedules |
| availability_exceptions | Custom dates and blocked periods |
| meeting_methods | Supported meeting methods |
| booking_holds | Temporary slot reservations |
| notifications | In-app notifications |
| admin_logs | Administrative activity records |
| platform_settings | Global website configuration |

### Database Requirements

- Use proper foreign key relationships.
- Use database indexes for booking queries.
- Validate data on the server.
- Maintain timestamps.
- Store booking history.
- Implement Row Level Security (RLS).
- Prevent unauthorized data access.

### Booking Status Lifecycle

**Booking Submitted → Pending → Approved / Rejected**

An approved booking can subsequently become Completed.

Additional statuses may include Cancelled, Rescheduled and Expired.

All status transitions must be validated on the server.

# 20. FINAL PRODUCT DEFINITION

## ETARNITY MEETING

### Connect. Schedule. Collaborate.

A centralized meeting booking and management platform that connects people with the right professionals at Etarnity Global Innovation.

**Core Product Specifications:**

- 03 User Roles
- 04 Core Board Member Dashboard Sections
- 10+ Major Feature Modules
- 100% Responsive Design Target

### Final Product Philosophy

The most important three parts of this project are:

1. Scheduling Engine.
2. Booking Conflict Prevention.
3. Role-Based Dashboard Architecture.
